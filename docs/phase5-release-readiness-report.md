## 검색과 평가 품질

표준 Fake 검색은 관련 15개 및 무관 11개 질의에서 Recall@5 **96.67%**, 무관 검색의 빈 응답 **0/11**이었다. Fake는 NFKC 토큰과 글자 바이그램을 768칸에 해시하고 최솟값 없이 정렬한다. 무관 질의의 최고 점수 범위는 **0.022646~0.266557**이었다. 같은 합성 표본의 사후 임계값 비교는 다음과 같다.

| Fake 최소 점수 | Recall@5 | 무관 질의 빈 결과 |
| --- | ---: | ---: |
| 적용 없음 | 96.67% | 0/11 |
| 0.12 | 96.67% | 6/11 |
| 0.15 | 86.67% | 8/11 |
| 0.30 | 56.67% | 11/11 |

0.12는 추가 유보 표본에서 검증할 후보다. 무관 후보 11개를 전부 제거하는 0.30은 관련 자료를 많이 잃었다. 이번 변경에서 Fake·Gemini 임계값과 SQL 사전 승인·실행 필터를 유지했다. 후보 표시와 장애 원인 판단을 UI에서 구분하고, 진단의 확인된 사실에는 직접 티켓 근거를 검증하는 기존 서버 제약을 유지했다.

실제 `gemini-embedding-2`의 합성 교육 SOP와 승인 사고 2건을 따로 색인했다. 메모리 관련 요청은 과거 사고 0.902926, SOP 0.828311, 시나리오 합성 스토리지 사례 0.674052를 반환했다. 한국어 조리법과 영어 철새 질문은 각각 결과 0건이었다. 관련 분석은 `gemini-3.5-flash-lite`에서 현재 티켓, SOP, 과거 합성 사고를 인용했고 티켓 사실과 가설을 분리했다. 무관한 조리법 요청의 분석은 인용·확인 사실·가설이 모두 비어 있었고 장애 분석 증거 부족을 알려줬다. 사용한 인용 링크의 허용된 원본 응답과 SOP 파일을 확인했다.

교육 피드백은 무조치, 교체 뒤 재검증 누락, 검증과 인계를 마친 미해결 티켓에서 동일 입력을 각각 3회, 총 9회 호출했다. 세 사례의 서로 다른 출력은 각각 **1, 3, 1개**였다. 무조치의 강점은 비어 있었고, 재검증 누락 사례의 대표 출력은 재진단과 기록을 권장했으며, 미해결 사례도 재검증 성공을 강점으로 표시했다. Gemini는 기존 판정의 강조 항목과 순서를 선택했고 서버 검증과 고정 문장 렌더링을 유지했다. 일관성은 서버 판정에 적용되며 강조 항목은 실행마다 달라질 수 있다. 교육 효과와 일반화는 소수 합성 질의만으로 판정할 수 없다.

## 백업과 복원

`python -m tests.qa_persistence --project polytech-qa-phase5-perf --restore-project polytech-qa-phase5-restore-final --origin http://127.0.0.1:18173 --restore-origin http://127.0.0.1:18177 --wait-timeout 240` · **통과**. 새 볼륨의 22개 테이블 행 수와 내용 지문, SOP 원본 8개의 SHA-256이 일치했다. 평가 4행, 티켓 평가 8행, 학습 기록 2행, 티켓 감사 46행, 최종 리비전을 포함한 인계 리비전 17행, 사고 자료 5행을 대조했다. 평가 입력 JSON·규칙·AI 설명·확정 요청 영수증·처리 중 lease는 포함 테이블의 전체 행 지문으로 검증했다.

복원 뒤 합성 교육 계정으로 API에 로그인해 완료 이력·인계·행동·작업·티켓 평가를 원본 응답과 비교했다. 동일한 확정 키로 원래 응답을 받고, 복원한 처리 중 lease를 만료시켰을 때 평가 Worker가 규칙·설명을 `READY`까지 처리했다. 최초 복원 실행의 API 단계에서 이름이 겹친 테스트 변수를 수정한 뒤 새 볼륨에 전체 절차를 재실행했다. 기존 볼륨과 운영 데이터는 보존했다.

별도 QA DB를 중단하면 로그인도 `503 DB_UNAVAILABLE`이 됐고 응답 요청 ID를 Nginx·FastAPI 로그에서 찾았다. `/health`는 200, 내부 readiness는 `503 DB_NOT_READY`였으며 DB 재기동 후 readiness와 티켓 조회가 회복됐다. 이는 통제된 장애에서의 관측이다.

## Windows 성능

Docker Desktop의 WSL2 커널 `5.15.167.4-microsoft-standard-WSL2`, Linux x86_64, 논리 CPU 18개, Docker 메모리 7.52 GiB, `overlay2`에서 계측했다. API의 프로파일 파일과 DB 초기화 파일은 bind mount, DB 데이터와 SOP는 named volume이다. 조사 당시 QA API·DB·worker의 `OOMKilled`는 모두 false였다. 부하는 기존 운영 API의 합성 데이터·최대 동시 5의 99개 표본과 추가 동시 인계 조회 20개다. 오류 0건이었고 HTTP 114개를 모두 동일한 요청 ID로 매칭했다. 분석 완료 5개는 별도 타이머로 측정했다.

| 티켓 | 20 | 42.79 / 65.70 | 38.00 / 62.35 | 31.54 / 55.19 | 9.40 / 19.03 |

단위는 ms다. 이 표본에서 Nginx 외부 시간 p95는 티켓 7.28ms, 동시 인계 8.22ms였다. 티켓·동시 인계의 풀 p95는 19.80ms와 12.60ms였다. Fake 임베딩 왕복 p95는 SOP 84.09ms, 해결 티켓 31.31ms였으며 실제 외부 모델 지연과 구분한다. 과거 Phase 1 최종 티켓 p95 1,092.95ms를 그대로 보존한다. 이번 실행은 그때의 큰 격차를 재현하지 않았고 각 실행이 다른 환경 표본이어서 속도 차이를 Phase 5 코드에 귀속할 수 없다. DB 인덱스와 PRD 500ms 목표는 유지했다. [Phase 1 성능 기준과 방법](test-stabilization-report.md)

## 배포 결정과 남은 위험

- **개발 완료.** 교육·운영 브라우저, 백엔드, 새 DB·레거시 업그레이드, Windows 임시 TLS, 별도 합성 복원, 실제 Gemini 스모크를 통과했다.
- **운영 배포 승인 보류.** 대상 Ubuntu와 운영 조건에서 다음 게이트를 완료한 후 판단한다.
- Ubuntu 배포 PC에 접근할 접속 정보가 없어 실제 Ubuntu 스테이징·도메인·공개 TLS는 미검증이다. 배포 서버에서 후보 커밋, 이미지 ID, 별도 볼륨, 성능, 로그인 503, 인증 경계, 실제 Gemini와 복원을 확인하는 명령을 제공했다. [Ubuntu 스테이징 절차](phase5-staging-runbook.md)
- 검색에서 관련 메모리 질문에 스토리지 자료도 한 건 포함됐다. 현재 기준의 후보와 근거 검증은 작동했지만, 실제 문서 규모와 별도 질의 집합에서 오인용과 설명 품질을 검증한다. 0007 마이그레이션은 사고의 Fake 임베딩을 시드한다. 실제 모델 시험의 벡터 반입은 합성 QA 전용이며, 배포 후보의 승인 자료를 목표 프로필로 준비했는지 별도로 확인해야 한다.
- 정상 운영 중의 과거 간헐 로그인 503 원인은 열려 있다. 정상 DB의 실제 QA 로그인 제한 재검증은 순차 401·200·401, 동시 18건은 401 11건·429 7건, 별도 IP 200, 버킷 회복 뒤 401이었고 503은 없었다. 대상 서버에서 동일 요청 ID로 Nginx, FastAPI 오류 종류와 SQLSTATE, PostgreSQL, Docker 재시작·OOM 정보를 대조한다. 사용자 가입과 실제 배포 승인은 대상 서버의 게이트가 끝날 때까지 보류한다.
