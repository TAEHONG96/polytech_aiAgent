# 교육 시뮬레이터 Phase 2 격리와 배포 검증

2026-11-22 · 작업 브랜치 `codex/phase2-simulation-isolation` · Phase 1 기준 커밋 `4dc9700`

Phase 2 개발 착수와 배포 검증은 독립적으로 진행한다. Phase 1 측정값과 당시 결과는 [Phase 1 안정화 보고서](test-stabilization-report.md)에 보존했다. 이번 작업은 별도 QA Compose 프로젝트, 합성 계정, PostgreSQL 볼륨에서 검증했다.

작업 브랜치는 안정화 커밋을 그대로 기반으로 한다. 로컬 `main`과 `dev`는 모두 이 기준 커밋의 조상이다. PRD·ERD·API 설계 문서와 프론트 잠금 파일을 보존했다.

## 구현 범위와 정책

| 영역 | 적용한 내용 |
| --- | --- |
| 인증·가입 | 기존 Argon2, HttpOnly 세션 쿠키, SameSite, Origin, CSRF 및 로그인 제한을 사용한다. 레거시 계정에 `operator` 역할을 부여하고 새 계정에는 DB 함수가 `trainee`만 할당한다. 런타임 DB 역할에는 `users` INSERT 권한을 부여하지 않는다. 사용자명은 영문·숫자와 `_.-` 3–64자로 받고 소문자로 저장한다. 비밀번호는 12–128자이며, 가입 뒤 기존 방식으로 로그인한다. 가입은 기본 비활성화 상태다. 격리된 로컬 개발 API의 `APP_TRAINING_REGISTRATION=1` 설정에서만 열리고 로컬 Nginx는 IP별 분당 3회와 버스트 3회를 적용한다. 운영·터널 프록시는 해당 경로를 차단한다. |

| 교육 실행 | 세션 사용자와 경로의 실행 UUID로 소유권을 확인한다. 쓰기 요청은 Origin·CSRF 확인 이후 소유 실행 행을 잠그고 ACTIVE 상태를 확인한다. 다른 계정의 실행 또는 같은 계정의 다른 실행에서 빌린 하위 ID는 404다. 완료 기존 자료는 조회 가능하며 티켓·작업·초안 수정 및 새 분석은 409다. |
| 티켓·작업·인계 | 공통 도메인 서비스의 상태 전이, 버전 충돌, 보관, 작업, 인계 스냅샷과 리비전을 재사용한다. 후속 작업은 부모 티켓과 함께 조회한다. 운영 회차·담당자 ID는 교육 배정에 사용되지 않는다. 발신 초안은 실행별 한 건이며 운영 보고서와 조회 경로를 구분한다. |
| RAG·SOP·출처 | 승인 SOP, 현재 실행의 미보관 해결 티켓, 대상 티켓 발생 전 승인된 동일 시나리오 사고만 검색 후보에 넣는다. 적용 조건은 SQL 순위 및 top-K 이전에 평가된다. 승인 사고 벡터에는 임베딩 프로필을 함께 저장한다. 티켓을 지정하지 않으면 공통 사고는 검색 대상에서 빠진다. SOP 원본, 사고 출처와 인용 대상의 현재 소유권·승인 상태를 원본 경로에서 확인한다. 레거시 SOP는 미승인으로 시작한다. |
| AI Worker·평가 | 저장한 요청자, 실행, 부모 티켓 또는 인계 리비전을 검증한 뒤 모델을 호출한다. 도구는 같은 실행 범위를 사용하고, 분석 조회에서 인용 원본과 경로를 다시 확인한다. 평가 조회는 완료된 소유 실행의 보고서와 티켓을 함께 검사하고 다른 실행의 티켓·이벤트·작업, 미승인 출처를 제외한다. |
| 화면·스키마 | 교육 계정은 로그인 후 내 실습으로 이동하고, 진입·재접속과 직접 실행 URL에 기존 세션을 쓴다. Alembic `0006_training_isolation`이 역할, 승인 필드, 실행 FK, 사고와 평가 조회용 테이블을 추가한다. |

교육 보고서 최종 확정, 규칙 계산·AI 설명 worker, 가상 조치 실행, 자료 승인·사고 벡터 발행 도구와 공개 가입 UI는 후속 범위다. 완료 실행과 평가 읽기 검증에는 격리 DB에서 준비한 합성 상태를 사용했다.

## Phase 1 후속 조사

### Docker 빌드와 잠금 파일

현재 Windows에서 npm 레지스트리의 DNS 조회와 HTTPS ping 200을 확인했다. 같은 잠금 파일로 `docker build --no-cache --target dependencies frontend` 및 운영 프론트 target의 깨끗한 빌드가 성공했다. Linux 이미지의 설치 패키지 29개에 대해 잠금 파일의 버전 및 무결성 값과 대조했고, 일치하지 않는 항목과 누락된 필수 패키지는 각각 0개였다. 이미지와 저장소의 잠금 파일 SHA-256은 `4dc0e1fd72e8faf2fd4ae9d98a9471e9719c15541c9984cf3300ef74aeeabbed`다.

Phase 1의 Playwright에 사용한 캐시 이미지에는 패키지 26개가 설치되어 있었고 이미지 자체의 잠금 파일과 설치 버전은 맞았다. 그 잠금 파일의 SHA-256은 `9eeca8793444627c699e540979b0e1952e2f8dee40948990601c8d2b030286b0`이었다. React 19.3.1과 Vite 8.3.8은 일치했다. 캐시 이미지는 현재 잠금 파일과 패키지 집합이 달랐다.

이전 `npm ci ETIMEDOUT`은 빌드 컨테이너의 의존성 설치 중 발생했다. 이번 깨끗한 빌드에는 재현되지 않았으며 당시 DNS, 프록시, 패키지 전송 중 어느 구간에서 끊겼는지 확인할 세부 로그가 남아 있지 않았다. 배포 후보를 만드는 CI의 깨끗한 환경에서 재현 가능한 빌드는 필수 게이트로 유지한다.

### 로그인 503

Playwright trace와 보존된 Nginx 로그에서 두 요청의 ID를 연결했다. 두 응답은 로그인 동시 부하 중 UTC 2026-11-20 15:20:50.033과 15:20:50.047에 시작한 요청의 HTTP 503 `DB_UNAVAILABLE`이었다. Nginx 완료 기록은 각각 15:21:00.100과 15:21:00.127로, 시작 시각과 약 10.07초·10.08초 차이가 있었다. 전후 2분 PostgreSQL 로그에서 재기동·종료·연결 슬롯 고갈의 근거를 찾지 못했고 보존된 FastAPI 로그에는 ID와 연결된 드라이버 오류가 없었다.

기존 오류 응답을 유지하면서 재발 시 요청 ID, 정규화된 라우트, 드라이버 예외 타입, SQLSTATE, 연결 무효화 여부를 API 로그에 남기도록 했다. 이전 503의 원인은 미확정이며 배포 전 확인한다.

Phase 2 QA DB를 통제된 조건에서 중단했을 때 `/health`는 200이고 로그인은 503 `DB_UNAVAILABLE`이었다. 응답과 Nginx·FastAPI 로그의 요청 ID가 일치했고 FastAPI에는 `route=/auth/login`, 드라이버 `OperationalError`, SQLSTATE `None`이 남았다. DB 재기동 뒤 내부 readiness 200을 확인했다. 이 시험은 진단 경로를 확인한 것이다.

보존된 티켓 조회 표본은 각 실행 20개다. 아래에는 이전과 동일한 원본에서 요청 ID별로 Nginx·FastAPI·클라이언트 측 시간을 연결한 결과를 기록했다.

최종 실행에서 차이가 가장 컸던 요청 `816be292-c8d6-4b55-8231-445763e455e3`의 클라이언트 시간은 1,192.04ms, Nginx는 258.00ms, 업스트림 연결은 1.00ms, FastAPI는 241.56ms였다. 나머지 934.04ms는 Windows HTTP 클라이언트의 연결 풀 대기, 연결 및 폴링 스케줄, Docker 포트 전달, 소켓에서 응답 읽기 시간을 포함한다. 이 차이를 DB 지연이나 Nginx 업스트림 연결 비용으로 판정할 증거는 없었다. 역사적 로그에는 Windows 측 세부 시각이 없다.

기존 Phase 1 API 이미지와 합성 DB를 다시 띄워 동일한 프록시를 대상으로 워밍업한 두 티켓을 조회했다. Windows의 루프백 포트와 Docker 내부 프록시 네임스페이스에서 각각 50건, 동시성 5로 요청했다. HTTP 클라이언트 추적과 Nginx 시간을 요청 ID 100개로 연결했다.

조회 전용 부하에서는 역사적 차이가 재현되지 않았다. 재현 시에는 전체 혼합 부하에도 같은 HTTP 추적을 적용하고 Windows 스케줄링과 포트 전달 구간을 같은 ID로 대조한다. 최근 수치를 역사적 기준값이나 독립 Ubuntu VM의 배포 판정으로 사용하지 않는다.

### Ubuntu VM 재검증 게이트

현재 접근 가능한 Docker context는 로컬 Docker Desktop이다. Windows에 등록된 Ubuntu WSL은 실행 시 `Wsl/Service/E_UNEXPECTED`가 발생했다. 독립 Ubuntu VM에서 실행한 성능 결과는 없다.

1. Windows 비교 실행과 Ubuntu VM에서 동일한 linux/amd64 API·worker·웹 프록시·PostgreSQL 이미지를 고정한다. 후보 이미지의 ID와 플랫폼을 기록하고 `docker save`와 `docker load`로 동일 이미지를 옮긴 뒤 Compose의 QA 오버레이에 태그를 지정한다. `up --no-build --pull never --wait`로 동일 이미지 ID를 확인한다.
2. Linux 파일시스템에 체크아웃하고 완전히 별도인 QA 프로젝트, 루프백 포트, 빈 named volume을 사용한다. 같은 Fake provider로 표준 평가의 `--prepare --phase-five`를 실행한 뒤 같은 교대와 표본을 준비한다.
3. [Phase 1 동일 부하 절차](test-stabilization-report.md#ubuntu-vm-동일-부하-재측정-절차)의 동시성 5, 표본 99, 폴링 100ms와 로그 계측을 사용한다. 부하 생성기의 위치와 CPU·메모리·스토리지 조건을 기록한다. 외부 Gemini 측정은 합성 스택에서 별도로 실행한다.
4. 요청 ID를 모두 대조하고 티켓·인계 등 비AI 주요 읽기의 종단 간 p95를 기존 **500ms** 기준과 비교한다. Windows 원본 기준값, Ubuntu 결과와 배포 후보별 측정값을 각각 보존한다.

## 실행한 회귀와 발견한 충돌

| 검증 | 실행 결과 |
| --- | --- |
| 백엔드와 교육 격리 | 격리 DB에서 `docker compose --env-file .env.example -p polytech-qa-phase2-final -f compose.yaml -f <QA 네트워크 오버레이> run --build --rm -T test python -m pytest -p no:cacheprovider -q --tb=short`로 실행해 **55개 통과**. 새 격리 케이스는 서로 다른 사용자, 같은 사용자의 두 실행, 직접 티켓·작업·리비전·분석·평가 ID, 완료 실행의 변경 차단, SQL top-K, SOP 승인 철회와 원본, 다른 실행 티켓이 연결된 worker 작업 거부를 검증한다. |
| Alembic | 격리된 빈 DB의 `alembic upgrade head`와 별도 합성 DB의 `0005_simulation_foundation` → `0006_training_isolation`을 검증했다. 기존 형식의 티켓 제목·상태·버전·NULL 실행 연결을 유지했고 운영 계정은 operator로 조회됐다. |
| 표준 RAG 평가 | 새 worker 컨테이너에서 `python -m app.agent.evaluation --prepare --phase-five`가 통과했다. Fake 평가 Recall@5는 96.67%였다. |
| 운영 Chromium | 격리된 6개 합성 회차로 표준 Playwright 테스트 **8개 통과**. 현재 잠금 파일을 사용한 Docker 개발 이미지에서 티켓, RAG/AI, 작업, 인계 초안·수정·확정·인수, Nginx 제한을 검증했다. |
| 교육 Chromium 및 로컬 가입 제한 | 두 교육 계정으로 로그인 뒤 교육 화면 이동, 소유 실행의 새로고침, 타인 실행의 직접 URL 404 표시, 운영 티켓 API 403을 확인했다. Nginx 네임스페이스의 별도 IP에서 동시 가입 8건은 201 네 건과 429 네 건이었고, 제한 코드와 응답 요청 ID가 일치했다. |
| 프론트 생산 빌드 | `docker build --no-cache --target production frontend` 최종 통과. 깨끗한 `npm ci`, TypeScript 검사와 Vite 빌드가 모두 실행됐다. |

초기 회귀의 운영 소유권 테스트가 역할 없는 모의 사용자로 403을 받아, 운영 역할을 가진 비소유자로 검증 조건을 명시했다. 교육 티켓 등록에서 기존 입력 검증을 중복 호출해 타임스탬프를 거부하던 경로와 교육 화면의 잘못된 모듈 참조를 수정했다. 반복 QA DB에서는 같은 점수의 기존 승인 사고가 남을 수 있어 검색 테스트 표본에 실행별 임베딩 프로필을 부여했다. Docker Desktop 기본 주소 풀이 소진된 QA 실행에는 프로젝트 전용 서브넷만 사용했다.

평가 쓰기·확정 연동과 실제 생성·평가 작업을 포함한 전체 훈련 흐름은 후속 검증 범위다. Phase 1 백업·복원 회귀는 기존 테이블을 비교한다. 배포 후보에서는 새 사고·평가 테이블에 합성 행을 준비해 복원 후 무결성도 확인해야 한다.
