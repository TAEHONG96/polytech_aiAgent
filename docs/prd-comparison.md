## 기존 PRD에만 명시된 보존 가치

| 항목 | 통합 초안 반영과 근거 |

| AI 실패의 수동 경로, 근거 부족 구분과 실행 trace | 교육 P0에서 근거가 부족할 때의 안내, 장애/인계 분석의 실패 상태와 시나리오 자료로 수동 작성하는 흐름을 유지한다. 도구명·순서·성공 여부·참조 ID는 실행 범위 안에서 열람한다. |

## 연계 설계 문서에서 정합화할 항목

| 쟁점 | 근거와 추천 처리 |
| --- | --- |
| 티켓 전이·CRUD 경로 | API 초안 §3.1은 기존 suffix와 전이 경로 재사용을 제시하나 §3.2는 `PATCH` 설명에 상태 변경을 포함하고 생성·보관·전이 경로를 열거하지 않는다. 현행 `PATCH`와 `/transitions`를 구분하고 생성·보관을 포함할 경로를 명시한다. 평가 예시 `RESOLVED`는 현행 `resolved`와 표현이 다르므로 티켓 상태는 소문자 계약을 기준으로 맞춘다. [API 초안](API_SPEC.md) · [현행 티켓](../app/tickets.py#L297) |
| 보고서 경로·버전과 종료 재시도 | 갭 분석의 scoped `/handovers/.../confirm`과 API 초안의 `/outgoing-handover/finalize`는 구현 후보가 다르다. 교육 외부 경로는 기존 서비스와 분리한 액션으로 두는 안을 추천한다. 현행 `expected_version`과 초안 `expected_revision`의 대응을 명시한다. ERD는 재시도에 409 또는 기존 결과를 열어 두고 API는 동일 키에 기존 결과를 제시하므로, 동일 요청 재전송은 기존 결과, 별개 경합은 충돌을 기본안으로 둔다. [갭 분석 §5](architecture-gap-analysis.md) · [API 초안](API_SPEC.md) · [ERD 초안](ERD.md) |
| 호스트 이력의 시점·공유 승인 | 티켓 기준 시각이 없는 `/hosts/{host_id}/incidents` 예시·ERD의 엄격한 감지시각 제약을 맞춰야 한다. 티켓 상세/AI에는 대상 티켓을 확실히 전달하고 일반 호스트 화면에는 별도 기준 시각을 명시한다. ERD의 `shared_approved` 기본값은 승인 없는 자료를 제외한다는 조건과 어긋날 수 있어 명시적 승인 전 비공개를 추천한다. [API 초안](API_SPEC.md#44-호스트-과거-사고-조회) · [ERD 초안](ERD.md#scenario_incidents) |
| 상태·식별자·평가 | `NOT_STARTED`는 현재 ACTIVE가 없는 홈 상태로 해석한다. 완료 행이 있으면 이력에서 `COMPLETED`로 표시한다. 분석 작업 ID와 실습 실행 ID를 이름·경로에서 구분한다. 평가 전체 상태와 규칙 결과의 조회 가능 여부를 분리하고 P0 상세 조회와 FR-11의 확장 UI를 구별한다. [v1.3 §4–6](PRD_v1.3.md) · [API 초안](API_SPEC.md#410-평가-상태티켓별-피드백) |
| 계정 권한·FK·마이그레이션 | 세션 응답의 현재 역할 표시는 고정값이다. 운영·교육을 병행할 때는 서버가 구분할 권한 정책이 필요하다. 기존 티켓/보고서 FK가 운영 사용자·회차를 참조하므로 가상 역할·슬롯 연결과 실행/시나리오 단위 참조 무결성을 확정한다. 과거 운영 행은 보존하고 교육 검색에서 제외한다. [인증](../app/auth.py#L76) · [모델](../app/handover/models.py#L11) · [ERD 초안](ERD.md) |
| 가입 요청·기존 세션·검증 오류 | 현행 로그인은 세션이 없는 요청에서 Origin을 확인하며 인증 후 변경은 Origin과 CSRF를 검사한다. 가입에도 적절한 Origin·요청 제한을 적용하고 세션 이전 CSRF 방식은 API 계약에서 결정한다. 기존 오류 봉투를 유지하며 교육 오류 코드와 실제 분석 DTO를 대조한다. [인증](../app/auth.py#L39) · [HTTP 처리](../app/http.py#L21) · [API 초안](API_SPEC.md) |

## 검증 범위와 다음 결정

- 현행 SPA는 로그인 후 티켓으로 이동하고 티켓·SOP·AI·인계 화면을 제공한다. 실습 홈·가입·실행별 메뉴·평가는 교육 전환에서 추가한다. 기존 분석 큐는 요청자와 작업 lease를 확인한다. 교육 평가를 같은 처리 기반에서 운용할지는 고정 입력·재시도·발행 경계를 대조한 뒤 결정한다. [SPA 진입점](../frontend/src/main.tsx#L305) · [분석 큐](../app/agent/queue.py#L55) · [갭 분석 §6·8](architecture-gap-analysis.md)
- 소스의 Alembic 체인은 `0001_ticket_foundation`부터 `0004_handover`까지다. `GET /health`는 `{"status":"ok"}`를 반환하고 `/api/v1/ready`는 적용 revision과 소스 head를 비교한다. 대상 배포의 적용 revision·볼륨·DB와 SOP 백업은 이번 분석에서 확인하지 않았다. [헬스](../main.py#L23) · [readiness](../app/db.py#L42) · [마이그레이션](../migrations/versions/0004_handover.py#L7)
- 기존 테스트 보고서는 Windows Docker Desktop 합성 환경에서 티켓 조회 p95 48.09ms와 실제 임베딩 RAG p95 465.77ms를 기록했다. 무관 질의 11개 중 1개에 검색 결과가 있었고, 생성은 모델·환경에 따라 실패와 성공이 모두 보고됐다. 대상 Ubuntu, 교육 격리 쿼리와 평가 처리 성능은 별도 검증 항목이다. [테스트 보고서](TEST_REPORT.md) · [알려진 문제](KNOWN_ISSUES.md)
- 구현 전 결정은 통합 초안 마지막 절에 모았다. 우선 가입·운영 경로 권한, 공통 코퍼스 승인, 가상 시간·배정 모델, 확정 차단 기준과 평가 범위를 확정해야 한다. 교육 API/ERD는 승인된 결정을 반영해 갱신한다. [통합 초안](PRD-merged-draft.md)
