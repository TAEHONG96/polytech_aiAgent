# AI 데이터센터 장애 대응 및 인수인계 교육 시뮬레이터

통합 PRD 최종 후보 · 2026-11-20 (KST)

교육 시뮬레이터의 제품 계약은 v1.3과 확정된 통합 정책을 따른다. 기존 PRD의 티켓·작업·근거 검토·인계 품질 규칙을 실습에 적용한다. 본문의 **기본안**은 구현 설계 권고다. 구현 전에 결정할 사항은 마지막 절에 모았다. [기존 PRD](PRD.md) · [PRD v1.3](PRD_v1.3.md) · [통합 전 비교 기록](prd-comparison.md) · [ERD](ERD.md) · [API 계약](API_SPEC.md)

## 1. 목적과 범위

학습자는 데이터센터 테크니션의 한 가상 근무 회차를 맡는다. 이전 근무자 Bot의 보고서를 받아 장애 맥락을 파악하고, 티켓·호스트 이력·SOP·Gemini 분석을 참고해 가상 조치와 후속 작업을 기록한다. 다음 근무자 Bot에게 인계할 보고서를 최종 확정하면 실습을 완료하고, 티켓별 행동과 증거를 바탕으로 피드백을 받는다.

| 사용자 | 역할 |
| --- | --- |
| 학습자 | 가입·로그인하고 본인 실행에서 티켓과 작업을 관리한다. 승인 자료를 검색하고 분석을 요청하며 인계 초안을 직접 수정·확정한다. 완료 결과를 조회하고 새 실행에서 재실습한다. |
| 이전·다음 근무자 Bot | 이전 Bot은 버전에 고정된 인수 보고서의 가상 발신자다. 다음 Bot은 실습자가 확정하는 보고서의 가상 수신자다. |
| 배포·교육 자료 운영자 | 자료와 고정 시나리오 버전을 검토·발행하고 배포·환경·백업/복원을 관리한다. 교육 MVP에서 자료 운영은 승인된 내부 절차로 수행하며 관리자 UI는 P1이다. |

| 범위 | 요구사항 |
| --- | --- |
| 교육 P0 | 개인 가입·실행 소유권, 불변 시나리오, 고정 교대·Bot 인수, 티켓·가상 조치·작업, 호스트 이력, 승인 SOP·RAG·Gemini, 인계·종료, 기본 종합 및 티켓별 규칙 평가, 완료 이력과 재실습 |
| 교육 P1 | 상세 종합 통계, 추가 난이도, 관리자 UI, 자유 시나리오 분기·대화형 Bot, 평가 점수 시각화와 확장 탐색 |
| 교육 범위 제외 | 실제 장비 제어·모니터링, 실제 다중 사용자 교대 협업, 동적 근무표 편집, 사용자별 물리 DB, 자율 다중 에이전트, 기존 운영 데이터 삭제 |

## 2. 실습 흐름과 시간

1. 가입한 뒤 기존 쿠키 세션으로 로그인한다. 진행 중인 실행이 있으면 이어하고, 새로 시작할 때는 발행된 시나리오 버전을 선택한다.
2. 대시보드에서 현재 조·고정 시나리오 시작 시각, 이전 Bot 인수 보고서, 티켓과 미해결·후속 작업, 다음 Bot을 확인한다. 인수 보고서의 티켓 링크는 현재 실행의 복제본을 가리킨다.
3. 티켓 상세, 호스트 이력, SOP·유사 사례 검색, AI 분석, 가상 조치·메모, 초안 사이를 자유롭게 이동한다. 검색·분석 횟수, 티켓 해결 개수, 보고서 열람 확인과 실제 경과 시간을 실습 진입이나 종료의 조건으로 사용하지 않는다.
4. 인계 후보·누락 질문과 수집된 자료를 검토한다. AI 초안을 요청하거나 수동으로 작성할 수 있고, 학습자가 수정·저장한다. 확인 후 최종 확정하면 시스템은 형식과 참조, 보고서 및 원본 자료의 버전 일치를 검사한다. 업무상 누락은 경고로 표시하고 확정 후 평가에 반영한다.
5. 확정 성공 직후 규칙 평가와 AI 설명의 상태를 각각 표시한다. 준비된 규칙 결과와 티켓별 타임라인·근거를 즉시 열람하고, AI 설명이 준비되면 강점·개선점·권장사항을 확인한다. 완료 기록은 이후에도 열 수 있고, 재실습은 새 실행으로 시작한다.

교육 환경은 **4조 2교대(A/B/C/D)**를 사용한다. 각 발행 버전에는 이전·현재·다음 **3개 근무 슬롯**과 인계 연결을 고정한다. 주간은 **08:00–20:00**, 야간은 **20:00–익일 08:00**이며 표시 시간대는 `Asia/Seoul`이다. 학습자는 현재 슬롯을 맡고 이전·다음 슬롯은 Bot이 맡는다. 장기 로테이션 계산은 MVP 범위에서 제외한다. 최초 학습자 슬롯은 주간(08:00–20:00)이다. 시나리오 시작 시각, 티켓·과거 장애 발생 시각 및 근무 슬롯은 발행 버전에 고정한다. 실습 기능은 실제 시간과 근무 종료 시각에 관계없이 이용할 수 있다. 서버 기록 시각과 이벤트 순번으로 사용자 행동을 정렬한다.

## 4. 상태와 업무 규칙

### 실행과 시드

- 실행 상태는 `ACTIVE`, `PAUSED`, `COMPLETED`다. 진행 중에 새 회차를 시작하거나 일시정지된 회차를 재개하면 현재 회차의 저장 기록을 보존하고 일시정지한다. 사용자당 `ACTIVE`는 최대 한 건이며 홈에는 새 실습 목록과 일시정지·완료 기록이 표시된다. 발신 보고서의 최종 확정 시 `COMPLETED`로 전환하고 평가를 예약한다.
- 발행된 시나리오에는 고정 초기 시각, 3개 근무 슬롯, 초기 실습·이월 티켓 템플릿, 호스트, 이전 Bot 보고서와 규칙 버전이 있다. 시작 시 템플릿을 새 티켓 UUID로 복제하고 원본 키와 평가 대상 분류를 보존하며, 보고서 링크를 현재 실행에 매핑한다. 동일 버전은 초기 내용이 같으며 사용자별 식별자와 활동은 독립적이다.
- 완료 후 티켓·조치·인계·학습 행동 원본은 읽기 전용이며 새 분석 요청도 차단한다. 평가 작업과 설명 결과는 고정 입력에 대해 별도로 갱신할 수 있다. 종료 후 완료되는 진행 중 분석은 분석 이력에만 저장한다. 평가 입력과 티켓 상태는 확정 시점의 값을 보존한다.

### 티켓과 가상 조치

- 티켓 상태는 `open`, `in_progress`, `waiting`, `resolved`, `closed`이고 우선순위는 P1–P4다. 새로 등록하는 티켓은 `open`이며, 초기 템플릿의 티켓은 발행된 상태를 따른다. `open`·`in_progress`·`waiting`은 미해결이다. 기존 전이, 해결 요약, 버전·감사 규칙과 미완료 작업이 있는 티켓의 `closed` 전이 제한을 적용한다. [현행 API 계약](API.md#티켓-상태-전이)
- 실행 중 티켓 생성·조회·수정과 `closed` 티켓의 보관을 지원한다. 보관 티켓은 기본 목록에서 제외하며 이력과 초기 실습·이월 티켓의 평가 자격을 보존한다. 담당자·담당 회차와 미배정 여부를 표시한다. 교육 배정은 실행 내 학습자·가상 역할·시나리오 슬롯을 사용하도록 설계한다.
- 후속 작업은 `todo`, `in_progress`, `blocked`, `done`을 사용한다. 담당자·마감·메모와 변경자의 이력을 표시한다. 티켓이나 작업의 상태·배정·필드 변경과 운영 메모는 시간순으로 열람한다.
- 가상 조치는 발행된 시나리오 규칙의 선행 조건과 결과에 따른다. 허용된 가상 조치만 교육 호스트와 티켓 상태를 변경한다. 자유 메모와 Gemini의 권고는 조치가 수행됐다는 증거로 사용하지 않는다. 실행된 가상 조치에는 행위자·시점·결과를 기록하며 요청 재시도에서 조치를 중복 적용하지 않는다.

### 근거와 AI

- 승인된 공통 합성 SOP·과거 사고와 현재 실행의 자격 있는 해결 사례를 근거로 사용한다. 동일 호스트 과거 이력을 조회하려면 대상 티켓을 지정한다. 이력 조회와 공통 사고 코퍼스의 검색·인용에는 명시적 승인과 `occurred_at < ticket.detected_at`를 적용한다. 대상 티켓이 없는 일반 지식 검색은 SOP와 현재 실행의 자격 있는 해결 티켓을 검색할 수 있다.
- 장애 분석은 진단 단계, 가설, 누락 정보, 근거와 불확실성을 제공한다. 기존 분석의 202 접수·폴링, 실행 시간 예산, 도구명·순서·상태·참조 ID를 계승한다. 인용은 문서 절/페이지와 사례·티켓 버전에 연결하고 열람 시에도 권한을 확인한다.
- 에이전트에는 읽기 전용 업무 도구를 제공한다. 티켓 변경과 작업 기록, 인계 확정은 인증된 학습자 요청을 도메인 서비스에서 검증한다. 근거가 부족하면 부족하다고 표시하고, 제공자 오류 시에도 사용자는 티켓과 작업을 조회·기록하고 수동으로 인계를 작성할 수 있다.

### 인계 후보와 보고서 확정

- 현재 회차·이전 이월·미배정에 해당하는 미보관 실행 티켓에서 미해결, 미완료 작업, 재확인 예정, 추가 승인 필요, 회차 중 변경을 수집한다. 해결 상태의 미완료 작업과 보류 작업도 표시한다. 수동 포함·제외는 실행 내 유효 티켓에 한정하며 초기 실습·이월 티켓의 평가 자격은 유지한다.
- 규칙으로 영향 범위, 담당 회차·담당자, 완료·미완료 작업, 다음 조치, 주의사항, 추가 승인, 대기 상태의 재확인 시각, 미완료 작업의 담당자·마감을 확인한다. 기록된 마감과 질문 대상자를 표시하고 학습자가 답변 또는 미확인 사유를 남길 수 있게 한다.
- 교육 UI는 편집 가능한 `DRAFT`와 읽기 전용 `FINALIZED`를 표시한다. 초안은 AI 작업 없이 빈 유효 문서에서 시작할 수 있다. 학습자가 최신 스냅샷과 리비전을 확인해 다음 Bot 앞으로 확정한다. 이전 Bot 보고서의 확인 이벤트는 선택 기능 후보로 두며 진행 조건으로 사용하지 않는다. 확정자·시각·고정 내용과 리비전 이력을 보존한다.
- 확정의 업무 검증은 **구조적 오류와 버전 충돌**만 차단한다. 요청·보고서의 형식 및 참조 무결성 오류는 구조적 오류다. 요약 내용이 비어 있거나 미해결 티켓·후속 조치·담당·재확인이 빠진 경우는 업무상 누락으로 경고하고 평가에 사용한다. 우선순위나 미해결 상태, AI 초안의 대기·실패 여부는 확정을 막지 않는다.
- 보고서 리비전이나 수집 이후의 원본 자료 버전이 달라졌으면 버전 충돌로 처리하고 다시 수집·검토한다. 경고 계산만으로 버전 충돌을 만들지 않는다. 최종 확정은 `POST /api/v1/simulation-runs/{simulation_run_id}/outgoing-handover/finalize`로 통일한다. 확정 리비전, `COMPLETED`, 고정 평가 입력과 예약을 한 트랜잭션에 기록한다. 같은 키로 같은 요청을 재전송하면 기존 결과를 반환한다.

## 5. 티켓별 평가와 피드백

- 입력은 확정 시점의 티켓과 작업, 감사·교육 행동 이벤트, 인계 버전 및 규칙 버전으로 고정한다. 확정 경고는 결과 화면에서 확인할 수 있게 보존한다. 초기 실습·이월 티켓에 해당하는 경고는 해당 티켓의 상세 평가에 반영한다.

| 티켓 출처 | MVP 처리 |
| --- | --- |
| 초기 실습 티켓 | 상세 규칙 평가 필수. 무조치·인계 누락·보관 여부와 관계없이 포함한다. |
| 이전 근무조 이월 티켓 | 상세 규칙 평가 필수. 이전 Bot 자료에서 넘겨받아 현재 실행에 복제하며, 초기 실습 티켓과 같은 기준을 적용한다. |
| 사용자가 실습 중 생성한 티켓 | 조치·후속 작업·인계·완료 이력은 보존한다. MVP 상세 규칙 평가와 상세 대상 집계에서는 제외한다. |
| 공통 과거 장애 이력 | 승인된 근거로 열람할 수 있다. 현재 실행 티켓으로 복제하거나 평가 대상·집계에 포함하지 않는다. |

- 규칙 판정은 서버가 `PASS`, `NOT_MET`, `NOT_OBSERVED`, `NOT_APPLICABLE`로 기록한다. 활동은 `ATTEMPTED` 또는 `NOT_ATTEMPTED`로 표시한다. 장애 이해, 호스트 이력 확인·활용, SOP 확인·활용, 가상 조치 타당성, 후속 검증, 문서화, 미해결 업무 인계를 평가한다. 소요 시간과 근무시간 준수 여부는 평가에서 제외한다.
- 적절한 후속 인계를 남긴 미해결 건도 긍정적으로 평가한다. 해결 상태라도 근거 없는 조치나 검증 부족은 개선점으로 남긴다. SOP 열람은 증거의 일부이며 올바르게 활용했는지는 연결된 행동과 기록을 기준으로 판단한다.
- 화면은 전체 요약과 티켓별 타임라인, 판정·증거, 강점·개선점·권장 사항을 제공한다. Gemini는 규칙 판정을 바탕으로 설명을 생성한다. AI 설명 대기·실패 중에도 준비된 판정과 근거를 읽을 수 있다.
- 규칙 평가는 `PENDING → PROCESSING → READY`로 진행하고 처리 실패를 `FAILED`로 표시한다. AI 설명은 `NOT_STARTED`에서 시작해 규칙 결과가 저장된 뒤 `PENDING → PROCESSING → READY`로 진행하며 실패를 자체 `FAILED`로 표시한다. 규칙이 `READY`이면 AI 상태와 관계없이 판정과 근거를 제공한다. worker 중단·lease 만료 복구와 중복 결과 방지를 적용하고 설명 재시도 시 저장된 판정을 보존한다.

## 6. 데이터 격리와 운영 호환

- 사용자 세션과 실행 소유권 검사를 **API·RAG·worker·출처 링크** 전체에 적용한다. 티켓·작업·이벤트·인계·리비전·AI 작업·평가 및 각 근거를 실행으로 묶는다. 같은 계정의 다른 실행도 현재 실행의 검색·도구 후보에 포함하지 않는다.
- 직접 ID, 커서, 보고서 수동 선택, 근거 링크, 원본 다운로드, 자동 색인·검색, worker·도구 allowlist, 브라우저에 보관되는 최근 분석 상태를 같은 권한 경계에서 검증한다. 승인된 공통 자료는 읽기 전용이다. 교육과 운영을 함께 제공하는 환경에서도 교육 계정은 공유 운영 경로에 접근할 수 없어야 한다.
- 기존 HttpOnly 쿠키·Argon2·Origin/CSRF·환경별 쿠키 보안과 `/api/v1`의 DTO·커서·버전·202 폴링·오류 형식의 호환성을 유지한다. 교육 업무 API는 실행 ID 접두사를 사용한다. 비소유 리소스는 404, 완료 후 변경·버전 충돌은 409를 사용한다. `GET /health`의 `{"status":"ok"}` 응답과 readiness 계약을 보존한다.
- 공통 자료는 승인된 합성 입력을 버전 관리한다. 기존 운영 DB의 행·SOP 원본·색인·리비전을 보존하고 운영 행을 임의의 학습자 실행에 연결하지 않는다. 교육 경계가 추가되면 빈 DB와 레거시 복제본에서 Alembic 업그레이드, readiness 및 DB와 SOP 파일 볼륨 복원을 검증한다.
- 현행 FastAPI, React·TypeScript·Vite, PostgreSQL/pgvector, Gemini, Docker Compose, Nginx, Alembic을 사용한다. DB와 SOP 파일은 named volume에 두고 DB 호스트 포트는 발행하지 않는다. Gemini 키는 worker 환경변수로만 제공하고 클라이언트·저장소·이미지·로그에 포함하지 않는다.

### 기존 운영 요구사항의 보존

| 영역 | 보존할 계약과 적용 범위 |
| --- | --- |

## 7. 품질, 검증과 전환 게이트

- 한국어를 기본 화면 언어로 사용한다. API는 오프셋을 포함한 시각을 입력받고 기존 업무 계약의 UTC 반환을 유지한다. 교육 시각 표현은 API에서 정한다. 핵심 제목·상태·오류를 키보드로 확인할 수 있고 상태를 문자로 확인할 수 있다.
- 기존 초기 규모인 동시 사용자 5명·티켓 1,000건 이하·검색 청크 10,000개 이하, 배포 후보의 비AI 주요 읽기 p95 500ms 이하, 단일 Ubuntu 호스트·RPO 24시간·RTO 2시간을 잠정 기준으로 유지한다. 교육의 실행 및 평가 규모와 배포 환경이 정해지면 다시 측정한다. [기존 개발 계획](TASKS.md) · [배포와 복구](DEPLOYMENT.md)
- 기존의 가상 스토리지 응답 지연 시연을 교육 회귀 사례로 유지한다. 과거 해결 사례·SOP를 확인하고 미완료 작업이나 담당자·재확인 누락을 남겨 수동 작성과 경고를 검증한다. 검색 근거 없음, Gemini 장애, 평가 worker 중단에서도 인계와 저장된 결과가 유지되는지 확인한다.
- 기본 통합·E2E는 API 키 없이 격리된 Compose에서 합성 자료와 Fake provider로 진행한다. 실제 Gemini 스모크는 승인된 합성 입력으로 따로 진행한다. 대상 배포의 실제 적용 revision, 볼륨, 백업 및 실제 Gemini 성능은 전환 전 확인한다. [기존 결과](TEST_REPORT.md) · [알려진 문제](KNOWN_ISSUES.md)

| 교육 전환 단계 | 범위와 통과 조건 |
| --- | --- |
| 1. 실행 기반 | 시나리오·실행·슬롯·호스트·복제 관계를 정의한다. 빈 DB 및 레거시 복제본의 업그레이드, 초기값, 동시 시작·부분 실패를 확인한다. |
| 2. 격리와 가입 | 티켓·SOP·RAG·API·worker·도구·출처 링크 전 구간을 검증한다. 두 계정, 동일 계정의 서로 다른 실행, 레거시 경로의 직접 접근과 검색 회귀를 통과한 후 교육 가입을 공개한다. |
| 3. 실습 업무 | 고정 3슬롯·Bot 보고서, 야간 경계, 동일 호스트 이력의 승인·발생 전 조건, 가상 조치와 근거 조합을 검증한다. 탐색·분석을 건너뛰어도 실습을 진행할 수 있다. |
| 4. 종료와 평가 | 구조 오류·버전 충돌의 차단, 업무 누락 경고 후 정상 완료, 변경과 종료 경합, 중복·롤백, 확정·평가 예약의 원자성을 검증한다. 네 가지 티켓 출처별 대상 범위와 worker 중단·AI 설명 실패 시 독립 상태를 확인한다. |
| 5. UX와 배포 | 가입→인수→자유 실습→최종 확정→티켓별 피드백→재실습을 브라우저에서 검증한다. 기존 계약·헬스·접근성 회귀와 격리 복원, 합성 Gemini 스모크를 확인한다. |

| D6 | 종료 설계 전 · 보고서와 Bot | 기존 리비전과 최신 원본 버전을 비교할 단위, 구조 검증의 세부 필드·경고 코드·수동 제외 사유, 이전 Bot의 선택적 확인 기록과 진행 중인 AI 작업의 완료 후 발행·취소 방식을 정한다. |

| D8 | 구현·전환 전 · 물리 모델과 배포 | 운영/교육 FK, 동시성 잠금, 내부 확정 상태 매핑과 규칙·설명 worker의 실행 구조를 정한다. 대상 서버·DNS/TLS·백업 위치, 적용 revision·색인 규모·복원 목표와 Gemini 모델 접근·쿼터·예산을 확인한다. |
