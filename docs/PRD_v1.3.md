# PRD v1.3 — AI 데이터센터 장애 대응 및 인수인계 교육 시뮬레이터

- 문서 상태: **설계 검토용(구현 전)**
- 기준일: 2026-11-20 (Asia/Seoul)
- 근거: 사용자와 합의한 PRD v1.2 및 `docs/architecture-gap-analysis.md`(Codex 정적 분석, dev `507a9ed`)
- 연계 문서: [ERD.md](./ERD.md), [API_SPEC.md](./API_SPEC.md)
- 표기: **확정** = 제품 요구사항, **제안** = 구현안(코드 검증 필요), **미확인** = 현행 실행/배포 확인 필요

## 1. 목적 및 제품 경계

실제 데이터센터 운영 시스템을 직접 제어하지 않는 **단일 근무 회차 기반 교육 시뮬레이터**다. 사용자는 이전 근무자 Bot의 보고서를 인수하고, 장애 티켓·호스트 이력·SOP/RAG·Gemini 분석을 자유롭게 이용하여 조치 내역을 기록하고, 다음 근무자 Bot에게 인계 보고서를 **최종 확정**하는 것으로 실습을 종료한다. 종료 후 **티켓별** 행동 근거 기반 피드백을 확인한다.

### 제품 성공 기준(P0)

1. 사용자별 회원가입·로그인 및 실습 이어하기가 가능하다.
2. 같은 불변 시나리오 버전을 선택한 사용자에게 동일한 초기 티켓·근무표·Bot 보고서가 제공된다.
3. 실습 수행 순서는 자유롭고, 보고서 **최종 확정만** 종료 트리거다.
4. 사용자 A의 티켓·조치·인계·AI 검색 결과가 사용자 B에게 보이지 않는다(직접 API, worker, RAG, 근거 링크 포함).
5. 호스트의 **발생 시점 이전** 장애 이력을 정확하게 조회하고, 관련 SOP/유사 사례와 함께 AI에 근거로 제공한다.
6. 미해결 티켓이 남아도 후속 조치가 보고서에 적절히 반영되면 종료할 수 있다.
7. 종료 직후 규칙 평가 상태를 제공하고, 준비되면 티켓별 근거·강점·개선점·권장사항을 볼 수 있다.
8. 완료 기록은 읽기 전용으로 보존하고 재실습은 새 실행 인스턴스로 생성된다.

### P0 / P1

- **P0**: 가입, 사용자별 실행/격리, 시나리오 시드, 고정 교대·Bot 인수, 기존 티켓·SOP·AI의 실습 컨텍스트, 조치 기록, 인계 확정/종료, 티켓별 규칙 평가 및 조회.
- **P1**: 상세 종합 통계, 추가 교육 난이도, 관리자 UI, 자유 시나리오 분기/대화형 Bot, 평가 점수 시각화.
- **범위 제외**: 실제 장비 제어·모니터링, 실제 다중 사용자 교대 협업, 물리 DB per-user, 동적 근무표 편집, 자율 다중 에이전트, 기존 운영 데이터 삭제.

## 2. 사용 시나리오 및 UX

1. **가입/로그인**: 기존 HttpOnly 쿠키 세션·Argon2·Origin/CSRF 보안 방식을 유지한다. JWT 전환은 요구사항이 아니다.
2. **시작/이어하기**: 실행 중인 ACTIVE가 있으면 해당 실행을 복원한다. 처음 시작하거나 재실습하면 고정 버전 시나리오에서 새 실행을 만든다.
3. **대시보드**: 현재 가상 근무조/시각, 이전 Bot 인계문, 현재 티켓 및 미해결/후속 작업, 다음 Bot 표시.
4. **자유 실습**: 티켓 상세↔호스트 과거 이력↔SOP 검색↔AI 분석↔가상 조치/메모↔보고서 초안을 어느 순서로든 오간다. 확인/분석 조회를 강제 관문으로 사용하지 않는다.
5. **인계 작성**: 티켓/작업/미해결 후속 조치를 반영한 AI 초안을 제공하고, 사용자가 수정·저장한다.
6. **최종 확정**: 보고서 필수 필드/버전/최신 스냅샷을 검사하고 사용자 확인 후 확정한다. **보고서 확정 + 실행 COMPLETED + 평가 작업 예약을 하나의 DB 트랜잭션**으로 처리한다.
7. **피드백**: 간결한 종합 화면에서 각 티켓을 선택해 타임라인, 평가 규칙, 증거, 강점, 개선점, 다음 수행 권고를 본다. AI 설명 대기/실패 시에도 규칙 결과를 조회할 수 있어야 한다.
8. **재실습**: 완료 실행은 수정되지 않고 새 실행으로 시작한다.

## 3. 운영 환경 및 시간

- **확정**: 4조 2교대(A/B/C/D), 주간 **08:00–20:00**, 야간 **20:00–익일 08:00**, 표시 시간대 `Asia/Seoul`.
- **확정**: 한 사용자 실습은 **현재 담당자의 한 근무 회차**에 한정한다. 이전/다음 근무조는 가상 Bot이며 실제 회원이 아니다.
- **확정**: 실제 벽시계로 실습 종료를 막지 않는다. 가상 시계는 초기 고정값에서 이벤트 기반으로 진행하고, 언제든 보고서 확정 가능하다.
- **제안**: 시나리오에는 이전·현재·다음 **3개 근무 슬롯**과 인계 연결만 필수로 포함한다. 4조 명칭/고정 시간은 유지하되 MVP에서 장기간 로테이션 계산 엔진은 만들지 않는다. 장기 순환 패턴은 별도 사양 승인 후 확장한다.
- **제안**: 가상 이벤트의 소요 시간은 시나리오 규칙에 정의하며 `virtual_now`는 단조 증가한다. 티켓 기록에는 실제 기록시각과 가상 발생시각을 구별해 저장한다.

## 4. 상태 및 핵심 불변식

### 4.1 시뮬레이션

- UI: `NOT_STARTED`(ACTIVE 실행 없음·과거 기록만 있을 수 있음), `ACTIVE`, `COMPLETED`.
- DB `simulation_runs.status`: `ACTIVE | COMPLETED`(NOT_STARTED는 실행 행 부재).
- 사용자당 ACTIVE 최대 1건, COMPLETED는 여러 건 허용.
- `COMPLETED`가 되면 기존 조치·티켓·인계 원본은 읽기 전용. 평가 작업 상태만 별도로 갱신 가능.
- 실습 완료를 위한 티켓 해결 개수·검색 횟수 제한 없음.

### 4.2 인계 보고서

- 기존 운영용 `DRAFT → READY → CONFIRMED → ACKNOWLEDGED` 및 리비전 구조를 보존한다.
- 교육용 UI는 `DRAFT`(편집 가능) / `FINALIZED`(읽기 전용)로 추상화한다. 내부에서는 기존 `CONFIRMED`를 최종 확정 상태로 매핑할 수 있으나 **실행 종료와 원자적 연결**해야 한다.
- 교육 모드의 수신 Bot은 실제 사람 ACK를 요구하지 않는다. 확정 후 추가 정정·인간 수신 확인은 교육 UI에서 비활성화한다.

### 4.3 티켓

- 현재 코드의 전이·버전·감사·해결 요약 제약을 유지한다. 실제 상태 enum은 기존 소스 계약을 우선하며 임의로 새로운 enum을 강제하지 않는다.
- 시나리오 시작 시 티켓을 신규 UUID로 복제하고 원본 템플릿 키를 보존한다.
- **공통 과거 사고**는 불변 합성 데이터, **현재 티켓·작업·분석·인계**는 실행 데이터다.
- AI의 권장은 작업 실행 이벤트가 아니다. 실행된 가상 조치와 사용자가 입력한 메모를 별도로 기록한다.

## 6. 티켓별 평가 정책

- 평가 입력은 **확정 시점의** 티켓/작업/감사 이벤트/인계 리비전과 평가 규칙 버전을 고정한다. 초기 티켓 중 보고서에서 누락된 것도 평가한다.
- 규칙 판정은 서버가 수행: `PASS | NOT_MET | NOT_OBSERVED | NOT_APPLICABLE`.
- 티켓 활동 분류: `ATTEMPTED | NOT_ATTEMPTED`(시뮬레이션에서 사용자가 조치하지 않은 티켓도 표시).
- 영역: 장애 이해, 과거 이력 확인/활용, SOP 확인/활용, 실제 조치 타당성, 후속 검증, 문서화, 미해결 작업 인계.
- **결과와 평가 분리**: 미해결이어도 적절한 후속 인계 시 긍정 평가; 해결됐더라도 무근거 교체·검증 누락은 개선 지적.
- SOP 페이지 조회만으로 '올바른 활용'을 PASS로 처리하지 않는다. 열람 이벤트는 근거 중 하나일 뿐이다.
- Gemini는 판정을 뒤집지 않고 자연어 해설만 생성. 설명 실패 시 규칙 결과는 제공하고 재시도 가능해야 한다.
- 완료 직후 평가 상태: `PENDING → PROCESSING → READY | FAILED`. 실패 이후 재시도 허용; 중복 평가 결과 금지.

## 7. 데이터·보안·운영 요구사항

- 고정 시나리오 버전과 승인된 합성 SOP/과거 사고는 공통 읽기 전용.
- 개인 실행: ticket/work/events/agent/handovers/results 모두 `simulation_run_id`로 범위를 유지하고 user 소유권 검증.
- 직접 ID, cursor, 근거 URL, agent tool allowlist, 비동기 worker, 재색인/검색에 동일 범위 적용.
- 교육 계정에서 공유 운영용 편집/삭제·수동 인덱싱·실제 사람 인수확인은 비활성화(기존 운영 기능 제거 아님).
- 타인 run/티켓 접근 시 외부에는 404, 완료 실행 변경 및 버전 충돌에는 409 기본안.
- 시나리오 이벤트/상태 변경은 재현 가능해야 하며 시드/규칙 버전 기록.
- 데이터 삭제·마이그레이션은 운영 DB에 임의 실행하지 않는다. 빈 DB와 레거시 복제본에서 검사.
- AI 호출 실패나 worker 중단으로 실습 데이터/완료 트랜잭션이 손상되면 안 된다.
- 별도 개인정보 수집 항목/보존 기간/공개 가입 정책은 서비스 공개 전 확정 필요.

## 8. 기존 기술/마이그레이션 제약

- 현행: FastAPI, React·TypeScript·Vite, PostgreSQL/pgvector, Gemini, Docker Compose, Nginx, Alembic.
- 기존 인증: HttpOnly 세션 쿠키/Argon2/CSRF. 기존 `/agent/analyze`는 202 큐 기반이고 worker는 lease를 사용한다.
- 기존 객체: `tickets`, `ticket_events`, `ticket_work`, `handovers` 및 리비전/항목, `shift_*`, `sop_documents`, `knowledge_chunks`, `agent_runs`/tool calls.
- **원칙**: 기존 로직 최대한 재사용, 기존 운영 API·데이터의 무단 삭제 금지. 교육 모드 경로를 명확히 분리.
- 현재 브랜치 정적 분석은 dev `507a9ed` 기준이므로 실제 작업 트리와 스키마 head 재확인 후 이행.

## 9. 개발 순서와 게이트

1. **Phase 1**: 시나리오/실행/호스트 관계·마이그레이션·초기값 복제·기본 테스트. 운영 DB 적용 금지.
2. **Phase 2**: 가입·소유권·티켓/SOP/RAG/agent/worker/인용 링크 **종단 간 격리**. 두 계정 및 동일 사용자 복수 실행 회귀 통과 전 외부 공개 금지.
3. **Phase 3**: 고정 교대·Bot 보고서·호스트 이력·가상 조치·AI 근거 조합.
4. **Phase 4**: 최종 확정 원자화·규칙 평가/고정 입력·Gemini 설명·실패 복구.
5. **Phase 5**: 프론트 전환·티켓별 평가 UX·재실습·기존 기능 회귀/E2E.

## 10. 미확인/확정이 필요한 구현 세부사항

1. 근무조 날짜별 장기 순환은 MVP 비대상. **3슬롯 고정 시나리오**를 기본안으로 제시하며 실제 조별 교대 패턴을 임의로 주장하지 않는다.
2. 사용자 가입 공개 정책/요청 제한, 중도 포기·초기화 허용 범위.
3. 어떤 기존 SOP와 합성 사고를 공유 승인할지, 호스트 표기/별칭 규칙.
4. 교육 평가 규칙·배점/보존 기간(초기는 규칙 결과만으로 충분).
5. 운영·교육 병행 배포 여부 및 기존 API 노출 정책.
6. 실제 운영 DB revision, 볼륨 백업, 기존 색인 규모·Gemini 성능은 **미확인**.
